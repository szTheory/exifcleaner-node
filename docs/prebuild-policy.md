# Native prebuild policy

## Authority

Native prebuilds are not committed to this repository. Each of the six
`prebuilds/<tuple>/publication.node` binaries is compiled on a matching-host CI
runner by `build-audit-native`, assembled and hash-checked by
`assemble-exact-native`, and shipped inside the tarball that `release.yml`
attests with `actions/attest-build-provenance`. That release attestation is the
only authority: nothing in this repository or its build scripts claims a
committed binary matches its source. `package.json`'s `files` entries are
unchanged and are how the six assembled prebuilds reach the published tarball
— they are how the tarball is packaged, not a claim about provenance.

## How a consumer verifies

Fetch the published tarball and check its attestation directly, without
trusting the registry alone:

```sh
npm pack exifcleaner-node@<version>
gh attestation verify exifcleaner-node-<version>.tgz --repo szTheory/exifcleaner-node
```

A tarball produced by this repository's release workflow verifies with exit
code `0`. A tampered copy — even a single flipped byte — fails: measured
locally against the published `exifcleaner-node@0.2.2`, `gh attestation
verify` exited `0` on the real tarball
(`2b454564345fdbaa3d26ace99b4ccee5fecfff9b74bdd374c1f6f97444e902ef`) and
exited `1` on a one-byte-flipped copy
(`22b5b362ce97dd755fbc5f91258af3d2db1806a10efb3db4e33c42896ac49950`) with no
matching attestation (`HTTP 404` from the attestations API; see the D-06b
entry in this phase's evidence for the full output).

A consumer can also check registry-level provenance from inside a project
that depends on the package:

```sh
npm install exifcleaner-node@<version>
npm audit signatures
```

This reports a verified registry signature and a verified attestation for the
package.

## Measured diagnosis

`npm run build:native` does not reproduce the committed prebuild it replaced,
and forced full rebuilds do not reproduce each other. This was measured fresh
on darwin-arm64 by forcing two full rebuilds (`rm -rf build` plus the tuple's
output before each `npm run build:native`, defeating node-gyp's incremental
no-op) and diffing the results against each other and against the
previously-committed blob.

Every differing byte across both comparisons falls into exactly three
regions, each independently mapped to a Mach-O load command or section via
`otool -l`:

1. **`LC_UUID`'s 16-byte UUID field** — a fresh random UUID generated by
   `ld64` on every link. Confirmed present and different in all three
   artifacts compared.
2. **One `LC_SYMTAB` nlist entry's 8-byte `n_value` field** — an embedded
   compilation timestamp. Decoded and cross-checked against each build's
   actual wall-clock build time to the second (for example, two sequential
   forced builds four seconds apart decoded to Unix timestamps four seconds
   apart).
3. **`LC_CODE_SIGNATURE`'s ad-hoc code-directory blob** — its `CDHash`
   changes on every comparison, consistent with the code directory hashing
   over the UUID- and timestamp-bearing header bytes above.

No differing byte appeared anywhere else: `strings` and `nm` diffs were both
empty across every pair compared, so no embedded path, symbol name, or symbol
address differs. The research hypothesis (`ld64`'s per-link random `LC_UUID`
cascading into the ad-hoc code signature) is **confirmed**. The `LC_SYMTAB`
compilation timestamp is an independently-traced addition the original
hypothesis did not name, decoded and confirmed rather than assumed. This
measurement covers darwin-arm64 only; the other five tuples were not measured
and no claim is made about them either way.

## Why deterministic committed blobs were declined

A committed binary cannot, by itself, be proven to match the source that
supposedly produced it — the diagnosis above shows real, unavoidable
per-build differences (linker UUID, embedded timestamp, ad-hoc signature)
that a byte-for-byte comparison would have to explain away on every release.
The release attestation instead proves origin directly: it binds the exact
tarball bytes to the exact CI run and workflow that produced them, which is a
stronger and simpler guarantee than reproducing a binary bit-for-bit.
Deterministic-build remediation (`SOURCE_DATE_EPOCH`, `-ffile-prefix-map`,
`ld64`'s `-reproducible`/`-no_uuid`, MSVC `/Brepro`, a CI double-build check)
stays deferred and is revisited only if an external auditor requires
committed reproducible binaries.

## Local development

`npm run verify` compiles the native publication addon by running `npm run
build:native` before `npm test`, so a local C toolchain is a prerequisite for
`verify`: Xcode Command Line Tools on macOS, build-essential on Linux, or
Visual Studio Build Tools with the C++ workload on Windows. `prebuilds/` is
gitignored, so running `build:native` locally never dirties the tree.

## Release-time negative control

`release.yml`'s `release` job runs a step named `Verify provenance and reject
a tampered tarball` immediately after `actions/attest-build-provenance` and
before any `npm publish` step. It verifies the admitted tarball with `gh
attestation verify`, then copies the tarball, flips its last byte, and
requires that same verify command to fail against the flipped copy —
inverting the exit code so an always-pass verifier turns the release red.
This runs only at release time, so it costs no per-PR CI minutes. A vitest
structural assertion (`tests/release_workflow_gate.test.ts`) fails if the
step is deleted, reordered after publish, loses its inversion, or drops its
`GH_TOKEN` environment variable.

## What is not permitted

Committing a prebuild binary to this repository, or publishing a tarball that
did not come out of the `assemble-exact-native` job's assembly and hash
check, are both refused by CI: `release_workflow_gate.cjs` requires every
publish job to depend on the full authority chain
(`immutable-sha-evidence` plus all six `installed-*` jobs) and rejects any
publish job that rebuilds or repacks after assembly.
